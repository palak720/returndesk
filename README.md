# ReturnDesk

A returns desk for a small online store. Agents raise return requests against an order, find them on a busy desk, and work each one through a fixed lifecycle (review, approve or reject, resolve, complete) with notes along the way.

**Repository:** _add the GitHub URL here_

Built with Next.js (App Router), TypeScript, Tailwind CSS, Node.js route handlers and PostgreSQL via raw SQL (`pg`). Validation uses Zod.

## Run it from a clean machine

You need Node 20 or newer and a PostgreSQL database (local, Docker, Neon, Supabase, ...).

```bash
git clone <repo-url> returndesk && cd returndesk
npm install

cp .env.example .env          # then put your connection string in DATABASE_URL
npm run db:setup              # runs the migration, then seeds the data
npm run dev                   # http://localhost:3000
```

`npm run db:setup` is `npm run db:migrate` followed by `npm run db:seed`, and works on an empty database.

- **Migrations:** `migrations/*.sql` run in filename order, each inside a transaction, and are recorded in a `schema_migrations` table so reruns are safe.
- **Seed:** 40 live requests that cover every status and every reason (every status and reason combination appears at least once), 52 notes, and 2 soft-deleted requests to show that removal keeps the record. If the database already has requests the seed stops and does nothing; run `npm run db:seed -- --force` to wipe and reseed.
- **Local Postgres with Docker:** `docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=returndesk postgres:16`, then use `postgres://postgres:postgres@localhost:5432/returndesk`.

### Tests

`npm test` runs black-box API tests (Node's built-in runner) against a running server, by default `http://localhost:3000`, or set `BASE_URL`. They cover all five business rules, validation, search, filter, sort and paging, and the error format. The tests create real rows with random order numbers, so point them at a development database rather than production.

### Deploying

Vercel plus Neon works with no extra configuration. Create a Neon database, set `DATABASE_URL` in the Vercel project, and run `DATABASE_URL="<neon url>" npm run db:setup` once from your machine to create the schema and seed it.

## API

All bodies are JSON. Money is a number with two decimals, timestamps are ISO 8601.

| Method and path | Purpose | Success |
| --- | --- | --- |
| `POST /api/requests` | Raise a request. The reference (`RD-001043`) is generated by the database. | 201 |
| `GET /api/requests` | List. Query: `q`, `status`, `reason`, `sort` (`createdAt`, `customerName`, `status`, `reference`), `order`, `page`, `pageSize` (max 100). Returns `{ data, meta: { total, page, pageSize, totalPages } }`. | 200 |
| `GET /api/requests/:id` | One request with all its notes, oldest first. | 200 |
| `PATCH /api/requests/:id` | Edit customer and item details (Open or In Review only). | 200 |
| `POST /api/requests/:id/transition` | Move through the lifecycle. Approving also carries `resolution` and `refundAmount`. | 200 |
| `DELETE /api/requests/:id` | Take off the desk (soft delete, Open or Rejected only). | 204 |
| `POST /api/requests/:id/notes` | Add a note. There is no edit or delete for notes. | 201 |
| `GET /api/health` | Checks the database connection. | 200 |

Every error has one shape, and is never HTML: `{ "error": { "code": "...", "message": "...", "details": ... } }`.

| Status | When | Codes |
| --- | --- | --- |
| 400 | Body is not valid JSON | `INVALID_JSON` |
| 404 | Unknown, malformed or removed id; unknown route | `NOT_FOUND` |
| 405 | Wrong method (with an `Allow` header) | `METHOD_NOT_ALLOWED` |
| 409 | Request is in the wrong state for the action | `INVALID_TRANSITION`, `REQUEST_LOCKED`, `NOT_REMOVABLE`, `DUPLICATE_LIVE_REQUEST` |
| 422 | Input fails validation, including rule 2 | `VALIDATION_ERROR` with a `[{ field, message }]` list |
| 500 | Only for genuinely unexpected failures | `INTERNAL_ERROR` |

## Design decisions

**Rules are enforced in the server, and the important ones twice.** The status flow lives in one map (`src/lib/domain.ts`) that the API checks and the interface reads to decide which buttons to show, so the two cannot drift apart.

**The database backs up the rules that must never be broken.**
- Rule 3 is a *partial unique index* on `(order_number, item_sku)` for rows that are not Rejected, not Completed and not removed. A "check, then insert" in application code can be beaten by two simultaneous requests; the index cannot. The resulting unique violation is mapped to a 409.
- Rule 2 is two `CHECK` constraints: a refund amount exists only with the `REFUND` resolution and must be above zero, and Approved or Completed requires a resolution. Zod gives friendly messages first; the constraints are the safety net.
- Status, reason and resolution are Postgres enums.

**Transitions, edits and removal run in a transaction with `SELECT ... FOR UPDATE`.** Two agents acting on the same request are serialised, so the second sees the new state and gets a clean 409 instead of overwriting.

**Soft delete with `deleted_at`.** Every read filters on it, the partial indexes exclude removed rows, and removing a request frees its order and item for a new one.

**Search, filter, sort and paging happen in one SQL query** with parameters for every value. Sort columns come from a whitelist, so the client never chooses SQL. Ties are broken by `id` so pages are stable. Wildcards typed by the user (`%`, `_`) are escaped and searched literally.

**References come from a Postgres sequence** (`RD-001001`, ...). They are unique, race-free, and the client cannot send one (unknown fields are rejected).

**Raw SQL instead of an ORM.** The queries are short, and the constraints and partial indexes are the interesting part, so I kept them visible in plain SQL.

**The interface keeps its state in the URL** (search, filters, sort, page), so a filtered view survives a refresh and can be shared. Search waits 400 ms after typing stops before it updates the URL, which is what triggers the request, and stale responses are aborted.

## Assumptions

The brief left these open, so I decided:

1. **Rejected is reachable from Open and from In Review**, not from Approved (approval is a decision).
2. **"Not yet decided" means Open or In Review**, so those are the statuses where details can be edited.
3. **The resolution is set only when approving**, in the same call as the transition, so there is no separate way to change it and bypass rule 2.
4. **Orders and items are plain fields** (`order_number`, `item_sku`, `item_name`), because the brief has no orders or products tables.
5. **Notes can be added in every status**, but not to a removed request (it can no longer be fetched, so it returns 404).
6. **A malformed id returns 404**, since it can never match a record.
7. **Search matches customer name, email, order number and reference** as a case-insensitive substring.
8. Money is shown in INR. The amount is stored as `numeric(10,2)` and has no currency column.
9. There is no login, because the brief does not mention one. Notes carry no author.

## What is incomplete, and what I would do next

- **No authentication or note authors.** Next step: agent accounts and an author on each note and status change.
- **No status history.** Only notes and the current status are stored. I would add an append-only log of transitions.
- **Substring search does a sequential scan.** That is fine at desk scale; with many rows I would add a `pg_trgm` GIN index on the searched columns.
- **No automated browser tests.** The API has tests; the interface was checked by hand, including at 375 px width.
- **Dates use the browser's locale and time zone.**
